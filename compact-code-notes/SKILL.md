# 紧凑源码学习笔记

写成可以连续阅读的技术笔记。让读者知道这一层解决什么问题、代码如何实现、为何这样实现，以及它和前后环节如何衔接。保留理解机制所需的细节，删掉对同一结论的重复解释。

## 开始前

- 从当前请求和已有对话确定主题、源码版本、输出位置，以及新建、续写还是精简。用户已澄清的信息直接沿用；只对影响正确性的缺失信息提问。
- 续写前阅读目标文档的目录和相关已完成章节，识别已讲概念、章节编号与当前进度。按用户指定位置写入；没有指定文件且无法从上下文确定时，先在回复中提供正文。
- 第一次使用时阅读 [风格样例](references/style-example.md)。用户提供的现有笔记优先决定文风和讲解密度；样例不可作为其他版本源码的事实依据。
- 查阅目标实现、直接调用方和必要的被调用方法。只追踪到足以回答当前机制的层级，不因某个 helper 出现就展开整个仓库。

## 组织理解路径

完整主题通常从入口和解决的问题开始，再介绍必要的数据表示与底层组件，接着讲执行路径、调用衔接与完整生命周期，最后才展开共享资源、性能优化或特殊适配。根据实际依赖调整顺序，不固定为 VE 的章节目录。

按“读懂下一段需要先知道什么”组织，而不是按文件顺序排列函数。同一职责的几个短方法可以放在一个小节。用户只要求讲一个函数时，保留理解该函数必要的上下文即可。

续写保持现有结构：前文已解释的组件用一句话说明本次作用并引用对应章节；还没展开的分支说明它在此处承担的职责，把细节留给后文。不要重贴前文的整段实现，也不要顺带补齐用户未要求的章节。

## 写好一个小节

默认采用以下行文顺序，而不把它们全部变成小标题：

1. **功能与位置。** 用一小段说明本段解决的问题、谁调用它，以及它交给下游什么结果或状态。
2. **必要源码。** 展示支撑说明的实现；短函数通常完整保留，长函数围绕语义完整的代码块选取。
3. **关键解释。** 按控制流或职责分组，连接条件、动作和后果，重点解释不直观的机制与实现动机。
4. **自然衔接。** 需要时说明下一步使用哪个结果、读取什么状态，或如何回到主调用链。已经清楚时直接结束。

简单委托函数往往一个代码块加一两段就够。复杂机制可以增加代码块和解释，但每段都应提供新信息，不按固定段数凑模板。避免在每个函数后重复附加“参数表、逐行解释、注意事项、类比、小结”。

## 解释到什么程度

- 写清关键分支的触发条件，以及该分支是返回、继续执行还是抛出异常。不要把“通常这样配置”写成“实现允许其他配置”；硬性检查、默认值和当前运行配置分别按证据表述。
- 调用关系包含方向和时机：谁创建对象，谁在何时调用方法，结果随后被谁使用。几个普通调用用正文即可；跨层主链可以用一个短 `text` 代码块，每条箭头表明调用或阶段推进，避免混成含糊的名称清单。
- 有状态对象要交代关键状态的设置方、使用方和释放或重置时机。按实际代码区分一次性准备、每次执行和清理阶段。
- 涉及张量、缓冲区或缓存时，解释引用、底层存储、复制与原地修改的区别，以及谁持有数据、谁写入、何时能复用。shape、dtype、设备、同步或梯度关系只在影响理解时展开。
- 解释“为什么”时落到具体后果，例如覆盖尚未消费的数据、重复累加或读取旧状态。实现意图若只是推断，明确其依据；没有调用方或运行证据时，不断言该分支已在实际任务中启用。
- 优化和兼容路径先讲清正确执行需要的条件，再讲复用或省略了什么；不要让优化细节淹没功能主线。
- 不把每个赋值、循环语法、类型标注都讲一遍。读者卡在某个细节时再局部展开，并把多轮问答归并为一段连贯解释。

## 源码与事实

以当前读取的实现为准，忠实保留标识符、条件、调用顺序和关键清理逻辑。文风可以沿用旧笔记，旧笔记中的拼写错误、过期事实或概括不能照搬。

新文档或跨文件章节简要标明仓库相对路径和核心符号；源码版本已知且会影响结论时注明版本。引用现有文档时沿用其导航方式，不在每段重复绝对路径和行号。

节选前明确说明删去了什么；非连续片段在缺口处用对应语言的注释标出省略。能够解释结论的分支、状态变更和异常清理应保留，不为缩短源码而改变其语义。伪代码或新增示例另行标注，不能伪装成原实现。示例只用于解决具体的理解障碍。

拿不到源码时，可以基于用户粘贴的片段写笔记，并简短标明依据和未确认的上下游。来源和证据边界集中说明一次；只在某处会改变读者判断时补充限定，避免每段重复“快照未提供”。不虚构调用点、实际配置、实验结论或性能数字，也不为写笔记自行启动训练或修改实现。

## 排版与语气

- 默认中文解释，保留英文代码标识符；自然、直接，使用连贯段落，省去对话开场和评价性套话。
- 新建长笔记可用 `# 1. 入口`、`## 1.1 初始化` 这样的编号标题；续写严格沿用原有层级和编号。标题表达功能，必要时附函数名，不把每个解释点都拆成标题。
- 代码围栏标注语言；正文中的符号用反引号；少量加粗用于容易混淆的关键结论。标题、代码块和列表前后留空行。
- 并列信息才用列表，多维比较才用表格。只在复杂关系通过图更容易理解时加入简图，不机械添加目录、流程图或结尾总结。
- 每段推进一个机制或因果关系；长段落按主题自然拆开，避免为了“紧凑”堆成文字墙。精简主要靠删重复和无关旁支，不靠省掉动机、重要边界或必要代码。

## 交付前

通读正文，核对代码与解释、分支与调用顺序、状态与资源生命周期是否一致。检查删减是否丢掉影响结论的条件，前文已讲过的内容是否重复展开，是否混淆了源码事实与推断。

编辑已有文件时只改请求范围，保留用户其他内容和暂存状态，不自行提交。写入后检查 Markdown 围栏、标题编号及链接。最终回复简短说明写到哪里和涵盖什么，不再在终端重复整篇笔记。
