# 紧凑源码学习笔记

写成可以连续阅读的技术笔记。让读者知道这一层解决什么问题、代码如何实现、为何这样实现，以及它和前后环节如何衔接。保留理解机制所需的细节，删掉对同一结论的重复解释。

每次按“确定理解问题 → 写作 → 核对事实 → 验收理解 → 修订复查”的顺序执行，主动完成检查，不等用户逐项提醒。检查规模随任务复杂度调整；检查问题与过程记录默认不加入笔记或 Q&A，也不另行创建检查报告。遵守要求的依据是正文能否支撑关键问题的答案，不能只声明“已按 skill 执行”。

## 开始前

- 从当前请求和已有对话确定主题、源码版本、输出位置、目标读者，以及新建、续写还是精简。用户已澄清的信息直接沿用；只对影响正确性的缺失信息提问。
- 续写前阅读目标文档的目录和相关已完成章节，识别已讲概念、章节编号与当前进度。按用户指定位置写入；没有指定文件且无法从上下文确定时，先在回复中提供正文。
- 核对当前讲解依赖的前置知识：区分目标读者可合理具备的基础知识、正文已经解释的概念，以及作者从源码或对话中才知道的背景。影响理解的背景在首次依赖处补齐；源码里存在、聊天中讲过或前文只提过名称，都不等于读者已经理解。
- 第一次使用时阅读 [风格样例](references/style-example.md)。用户提供的现有笔记优先决定文风和讲解密度；样例不可作为其他版本源码的事实依据。
- 查阅目标实现、直接调用方和必要的被调用方法。只追踪到足以回答当前机制的层级，不因某个 helper 出现就展开整个仓库。
- 动笔前列出少量本节必须回答的理解问题，优先使用用户已经提出的困惑，再据此组织讲解与验收。问题应涉及来源、原因、调用时机、状态变化或后果，不能只是“有没有提到某个函数”。复杂主题至少覆盖一条跨模块、跨阶段的完整链路，避免只逐个函数验收。

## 组织理解路径

完整主题通常从入口和解决的问题开始，再介绍必要的数据表示与底层组件，接着讲执行路径、调用衔接与完整生命周期，最后才展开共享资源、性能优化或特殊适配。根据实际依赖调整顺序，不固定为 VE 的章节目录。

按“读懂下一段需要先知道什么”组织，而不是按文件顺序排列函数。同一职责的几个短方法可以放在一个小节。用户只要求讲一个函数时，保留理解该函数必要的上下文即可。

把章节串成围绕主题推进的主线。进入新小节时，承接前文的结果、状态或尚未解决的问题，说明为什么现在需要讲这一环节。展开底层函数前，先交代它对应前文流程中的哪一步；若中间经过包装函数或回调，用一句话或短调用链补齐关系，再进入实现细节，让读者既能理解单个函数，也能把它放回整体流程。

新出现的对象、术语和状态先交代来源与当前职责，不依赖读者自行从代码猜测。上下文串联要落到具体的调用、数据或因果关系，不能仅用“接下来”“然后”等过渡词连接孤立的代码讲解。

续写保持现有结构：前文已解释的组件用一句话说明本次作用并引用对应章节；还没展开的分支说明它在此处承担的职责，把细节留给后文。不要重贴前文的整段实现，也不要顺带补齐用户未要求的章节。

## 文末 Q&A

- 每份笔记末尾保留一个独立的 `Q&A` 章节，用于收录用户指定的补充问答，与正文主线分开。章节标题沿用全文层级；续写正文时插在 Q&A 之前，保持它位于文末，不重复创建。
- 只有用户提问并明确要求将该问题加入文档时，才收录对应的问题与回答。普通对话中的提问不自动写入；尚无收录内容时，章节只有标题，不预填编号、问题或占位说明，也不自动整理历史问答填充。
- 收录的问题从 `1` 开始按 `1、2、3……` 连续编号，已有问答则接续编号。以编号和问题作为小标题，回答放在其下；问题编号独立于正文章节编号，不使用 `9.1` 之类的多级编号。

## 写好一个小节

默认采用以下行文顺序，而不把它们全部变成小标题：

1. **功能与位置。** 用一小段说明本段解决的问题、谁在什么阶段调用它，以及它交给下游什么结果或状态。
2. **必要源码。** 展示支撑说明的实现；短函数通常完整保留，长函数围绕语义完整的代码块选取。
3. **关键解释。** 按控制流或职责分组，连接条件、动作和后果，重点解释不直观的机制与实现动机。
4. **自然衔接。** 需要时说明下一步使用哪个结果、读取什么状态，或如何回到主调用链。已经清楚时直接结束。

简单委托函数往往一个代码块加一两段就够。复杂机制可以增加代码块和解释，但每段都应提供新信息，不按固定段数凑模板。避免在每个函数后重复附加“参数表、逐行解释、注意事项、类比、小结”。

精简前检查：删掉这段后，读者能否仍然理解为什么这样做，以及省略该操作会有什么后果？支撑主线推理的前提、机制和边界应保留；不影响这些理解的旁支可以省略。让取舍依据理解需要，不以字数短或函数名已出现作为讲解充分的标准。

## 解释到什么程度

- 识别“释放资源”“重建状态”“挂载回调”等压缩了多步行为的抽象表述。在关键处展开到操作前的状态、实际改变、操作后的状态，以及谁随后使用结果。例如，把方法保存到对象属性上时，说明保存的是哪个对象的方法、赋值是否执行它，以及后续由谁读取属性并调用；不能仅用另一个抽象术语替换原词。
- 写清关键分支的触发条件，以及该分支是返回、继续执行还是抛出异常。不要把“通常这样配置”写成“实现允许其他配置”；硬性检查、默认值和当前运行配置分别按证据表述。
- 调用关系包含方向和时机：谁创建对象，谁在何时调用方法，结果随后被谁使用。几个普通调用用正文即可；跨层主链可以用一个短 `text` 代码块，每条箭头表明调用或阶段推进，避免混成含糊的名称清单。
- 有状态对象要交代关键状态的设置方、使用方和释放或重置时机。按实际代码区分一次性准备、每次执行和清理阶段。
- 涉及张量、缓冲区或缓存时，解释引用、底层存储、复制与原地修改的区别，以及谁持有数据、谁写入、何时能复用。shape、dtype、设备、同步或梯度关系只在影响理解时展开。
- 解释“为什么”时落到具体后果，例如覆盖尚未消费的数据、重复累加或读取旧状态。实现意图若只是推断，明确其依据；没有调用方或运行证据时，不断言该分支已在实际任务中启用。
- 优化和兼容路径先讲清正确执行需要的条件，再讲复用或省略了什么；不要让优化细节淹没功能主线。
- 不把每个赋值、循环语法、类型标注都讲一遍；但语法若决定当前机制，例如保存方法与调用方法的区别，应主动解释到读者能跟上流程。已有追问暴露的理解障碍，在获准修订对应正文时归并成连贯解释。

## 源码与事实

以当前读取的实现为准，忠实保留标识符、条件、调用顺序和关键清理逻辑。文风可以沿用旧笔记，旧笔记中的拼写错误、过期事实或概括不能照搬。

默认面向不了解原仓库的技术读者。依据非公开框架或内部仓库写笔记时，正文省略仓库名称、内部文件路径、机器信息和提交版本；这些定位信息对读者没有导航价值。核对实现时仍追踪实际源码与调用方，写作时用 trainer、模型管理层、调度器等职责说明代码的位置和关系。

把这类实现作为设计示例引入，例如“一些框架会由 trainer 统一协调捕获；下面的实现通过两个回调，把 encoder 的捕获接入 LLM 的建图流程”。保留有助于理解的真实源码、函数名和类名，在章节开头说明它们属于示例即可，不必每段重复，也不要暗示读者可以查阅某个公开仓库。把特定配置、限制和执行顺序归于该示例，避免写成所有框架或底层库都必须遵循的规则。

若讲解的是读者可访问的开源项目，或用户明确要求仓库内的阅读导航，再按需提供相对路径和核心符号；版本影响结论时注明版本。沿用已有笔记的导航方式，但不延续与当前读者和用途冲突的路径引用。

节选前明确说明删去了什么；非连续片段在缺口处用对应语言的注释标出省略。能够解释结论的分支、状态变更和异常清理应保留，不为缩短源码而改变其语义。伪代码或新增示例另行标注，不能伪装成原实现。示例只用于解决具体的理解障碍。

拿不到源码时，可以基于用户粘贴的片段写笔记，并简短标明依据和未确认的上下游。来源和证据边界集中说明一次；只在某处会改变读者判断时补充限定，避免每段重复“快照未提供”。不虚构调用点、实际配置、实验结论或性能数字，也不为写笔记自行启动训练或修改实现。

## 排版与语气

- 默认中文解释，保留英文代码标识符；自然、直接，使用连贯段落，省去对话开场和评价性套话。
- 新建长笔记可用 `# 1. 入口`、`## 1.1 初始化` 这样的编号标题；续写严格沿用原有层级和编号。标题表达功能，必要时附函数名，不把每个解释点都拆成标题。
- 代码围栏标注语言；正文中的符号用反引号；少量加粗用于容易混淆的关键结论。标题、代码块和列表前后留空行。
- 并列信息才用列表，多维比较才用表格。只在复杂关系通过图更容易理解时加入简图，不机械添加目录、流程图或结尾总结。
- 每段推进一个机制或因果关系；长段落按主题自然拆开，避免为了“紧凑”堆成文字墙。精简主要靠删重复和无关旁支，不靠省掉动机、重要边界或必要代码。

## 交付前

把写作和审阅分开，完成初稿后依次检查：

1. **事实核对。** 对照源码核对代码与解释、分支与调用顺序、状态与资源生命周期。检查删减是否丢掉影响结论的条件，是否混淆源码事实与推断，是否把示例约束泛化成通用要求。
2. **理解验收。** 仅依据正文回答动笔前列出的理解问题，逐题形成简短答案并定位支撑答案的具体解释；缺少依据的标出缺口，不能用源码细节或聊天记忆补全。再以尚未读过源码的读者视角检查：每个小节为什么出现在这里，新函数从哪里被调用，本节结果如何被后文使用。源码、术语或标题出现过不代表读者已能理解。
3. **修订复查。** 在本次授权范围内补齐缺失的前提、机制或关系，必要时调整讲述顺序，再核对受影响的事实与理解问题。不用重复整段实现弥补上下文，也不为通过检查扩写无关内容。无法确认的内容明确标出依据边界，不能把它算作已解决。
4. **结构检查。** 写入后检查 Markdown 围栏、标题编号、链接、文末 Q&A，以及是否残留读者无法使用的内部定位信息或重复展开已有内容。能机械判定的要求可用程序检查；格式和关键词检查通过，不能代替前面的事实与理解验收。

例如，验收“为什么需要重建缓冲区”时，仅找到 `rebuild()` 的调用不算通过；正文还需解释旧存储的来源、重建解决的问题与新存储的用途，具体原因以当前实现为准。

对复杂主题，可在任务授权和环境能力允许时增加独立读者审阅：只提供笔记、目标读者背景和理解问题，让审阅者依据正文回答并指出缺口。独立审阅用于减少作者盲点，不代替源码核对，也不作为每次写作的前提；自己换个视角检查不能声称完成了独立审阅。

编辑已有文件时只改请求范围，保留用户其他内容和暂存状态，不自行提交。最终回复简短说明写到哪里和涵盖什么，如实说明仍未确认的关键内容，不再在终端重复整篇笔记或附上整套检查过程。

## 验证 skill 的效果

在评估本 skill 的修改效果时，用真实、具有代表性的写作任务检查生成笔记，纳入曾暴露理解缺口的问题，并覆盖复杂的跨模块或跨阶段讲解。比较修改前后的答案依据、事实正确性与讲解密度，不以规则数量或关键词命中判断改进。skill 文件的格式校验只证明格式符合要求；没有做实际写作评估时，不宣称已经验证了写作效果或能保证每次完全遵守。
